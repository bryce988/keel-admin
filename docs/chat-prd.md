# Keel · 即时通讯（IM）产品文档

> 版本 v1.0 · 2026-09-21 · 目标里程碑 **M5**

## 1. 一句话

给 Keel 加一个**内部员工即时通讯**模块：后台和员工移动端都能直接对话，形态参考钉钉，
但这一版只做「能聊」这一层——发得出、收得到、不丢不乱、换设备还在。

---

## 2. 背景与目标

Keel 到 M4 为止是纯脚手架，所有模块都是「表单 + 列表 + 权限」这一类形态。
聊天是第一个**形态完全不同**的模块，它同时压三件框架还没验过的能力：

| 能力 | 现状 | 聊天会压到 |
|---|---|---|
| 长连接 | 没有。全站都是短请求 | WebSocket 进程、断线重连、跨进程广播 |
| 跨端共用一份业务逻辑 | `common/service` 有，但只跑过读接口 | 后台与 staff 收发同一批消息，必须实时互通 |
| 非 RBAC 的可见性 | 全站可见性都由数据权限 Scope 决定 | 聊天的可见性由**会话成员关系**决定，部门维度在这里是错的 |

所以这个模块的价值不只是功能本身，它是框架的第三块试金石（前两块是 M1 的用户管理、M3 的个人中心）。

**可验证的目标**

- 两个员工能在后台互发文本 / 图片 / 文件，端到端时延 P95 < 500ms
- 刷新页面、断网重连、换一台设备登录，消息**不丢、不重、不乱序**
- 未读数在「顶栏红点 / 会话列表 / 浏览器标题」三处永远一致
- 员工移动端 `staff/` 与后台消息互通，服务端只有一份实现

## 3. 范围划线

**这一版做**

> 状态列：✅ 已完成 · 🚧 部分完成 · ⬜ 未开始。截至 2026-09-20，第 ①②③ 批已交付。

| 状态 | 功能 | 说明 |
|---|---|---|
| ✅ | 单聊 | 任意两名在职员工之间 |
| ✅ | 群聊 | 手动建群、加人踢人、改群名、退群、解散。群主不能直接退群（群会没人管），必须先解散 |
| ✅ | 文本消息 | 纯文本 + emoji，单条上限 5000 字 |
| ✅ | 图片消息 | 单张 ≤ 10MB，聊天窗口内直接预览 |
| ✅ | 文件消息 | 单个 ≤ 20MB（沿用 `sys.upload.maxSize`），点击下载。⚠️ **App 端发不了任意文件**——`uni.chooseFile` 只有 H5 与微信小程序有，App 上只能发图片 |
| ✅ | 会话列表 | 按最后一条消息倒序，支持置顶、免打扰、删除会话 |
| ✅ | 通讯录 | **在消息页左栏里，与会话列表并列**（切页签，不是独立菜单）。按部门筛选、按姓名搜索，点人直接开会话。移动端是独立 tab |
| ✅ | 未读数 | 会话级 + 全局汇总，红点与角标 |
| ✅ | 单聊已读 | 只在我发出的**最后一条**下方显示「已读 / 未读」。逐条标在单聊里没有信息量——对方读到哪条，前面的必然都读过了 |
| ✅ | 历史消息 | 向上翻页加载，不限时间范围 |
| ✅ | 撤回 | 自己的消息 2 分钟内可撤回（参数 `chat.message.recallWindow`）。**群主可撤回群内任意消息且不受时限**——本人撤回的两分钟是给手滑兜底，群主撤回是管理动作，限时两分钟等于这个功能不存在 |
| ✅ | @ 提醒 | 后台输入 `@` 自动弹成员面板；移动端用一个明确的 `@` 按钮（软键盘已占半屏，从输入里推断意图容易在打邮箱时误触）。被 @ 的消息气泡带强调边框，会话列表显示「有人@我」 |
| ✅ | 新消息提醒 | 后台：桌面通知 + 提示音，开关在聊天页标题栏。移动端：tab 角标 + 震动，**不做系统通知**（要接厂商推送，与「不绑死服务商」冲突） |
| ✅ | 发送失败重发 | 失败标红 + 「重发」，复用原 `client_msg_id`，不会变成两条 |

**这一版明确不做**

| 不做 | 为什么 |
|---|---|
| 群已读回执（谁读了、几人已读） | 单聊的已读是一个水位数字，零额外写入就能算出来；群里 N 人 × M 条要另起一张明细表，写入量随群规模平方级增长。这是 IM 里最贵的功能之一，等真有人要再做 |
| 音视频通话 | 需要引入 SFU / 第三方 RTC，与「脚手架不绑死服务商」的原则冲突（M3 换绑手机不用短信是同一条理由） |
| DING / 已读强提醒、待办转化 | 钉钉的这套建立在已读回执之上，前者不做后者就无从谈起 |
| 机器人、群 webhook、开放平台消息接口 | `app/open` 还是空壳，没有第一个真实接入方之前做就是死代码 |
| 外部联系人、跨企业会话 | 身份体系只有 `sys_users` 一套，C 端 `app_users` 与员工**永不混用**（PROJECT.md §8.4） |
| 消息编辑 | 撤回重发已经覆盖了绝大部分场景，编辑要维护版本历史 |
| 聊天记录云端搜索 | 见下面 V1.1 |
| 会话审计后台（管理员查看他人聊天记录） | 这是合规功能，牵扯授权流程与二次确认，单独立项，见 §8 |

**V1.1 候选**（不阻塞 V1 上线，按需求排优先级）

- 聊天记录搜索（按关键词 / 按人 / 按时间）
- 在线状态与「正在输入」——钉钉本身都不展示在线态，收益低于跨进程状态同步的成本，先放着
- 消息转发、合并转发
- 表情回应（reaction）
- 群公告、群文件

## 4. 角色与可见性

**聊天不套细粒度 RBAC。** 全站其他模块是「有没有这个权限点」，聊天是「在不在这个会话里」——
这两件事不能混。具体：

| 层面 | 规则 |
|---|---|
| 功能开关 | 权限点两个：`chat:use`（发消息）与 `contact:view`（看通讯录），内置角色默认都给。拆开是因为可能只给后者——比如外包人员能找到人报事，但不给他发起会话 |
| 能和谁聊 | V1 **全员可达**：能在通讯录里搜到任何在职员工并发起单聊 |
| 会话可见性 | 只有会话成员能读写该会话，非成员一律 404（不是 403，与全站「404 掩盖无权访问」的约定一致） |
| 看得到谁 | 通讯录对**全公司**可见，不受部门数据权限约束。但**手机号与邮箱仍受字段级权限管**（`sys:field:user:phone` / `:email`），没授权的看到掩码——「能看到这个人」和「能看到他的手机号」是两件事 |
| 数据权限（部门 Scope） | **不挂**。总部给分公司发消息是聊天最基本的用法，按部门过滤等于把功能废掉 |
| 管理员 | 超级管理员**不能**旁观他人会话。要看聊天记录必须走 §8 的审计流程，而不是靠 `is_super` 绕过 |

> ⚠️ 「全员可达」是**产品决策不是技术限制**。若将来要限制（比如实习生只能联系本部门），
> 加一条「可达范围」策略即可，服务端的成员校验位置不用动。这一层在 V1 就预留了，见技术文档 §4.3。

群内角色只有两种：

| 角色 | 能做 |
|---|---|
| 群主 | 加人、踢人、改群名/群头像、撤回任意消息、转让群主、解散群 |
| 成员 | 发消息、撤回自己的消息、退群 |

不做管理员这一档。三层角色在几十人的内部群里没有实际用处，只会多一套授权判断。

## 5. 功能详述

### 5.1 会话列表

左栏常驻，按 `last_msg_at` 倒序，置顶的排在最前。每一行展示：

头像 · 名称 · 最后一条消息摘要 · 相对时间 · 未读角标

- **摘要规则**：文本截前 30 字；图片显示 `[图片]`；文件显示 `[文件] 文件名`；
  撤回后摘要变成「xxx 撤回了一条消息」。群聊摘要前面带发送人昵称
- **时间显示**：今天显示 `HH:mm`，昨天显示「昨天」，本周显示星期，更早显示 `MM-DD`
- **未读角标**：99 以上显示 `99+`；免打扰的会话**只显示小圆点不显示数字**，也不计入全局未读数
- **有人 @我**：角标左边加「@」字样，优先级高于普通未读
- 右键菜单：置顶 / 免打扰 / 删除会话
- **删除会话 = 只从我的列表里移除，不删消息**。对方那边不受影响；
  对方再发一条，会话会带着新消息重新出现，但我看不到删除之前的历史。
  这是钉钉、微信的一致行为，用户预期如此

**空态**：一条会话都没有时，用 `<EmptyState>`（M3 的组件），动作是「发起会话」。

### 5.2 发起会话

- 入口：左栏的「通讯录」页签。**不做成独立菜单**——想给同事发条消息要先去别的页面
  找人再跳回来，平白多一次切换；常驻在左栏里，找人和聊天是连着的（钉钉桌面端同此）
- 通讯录里按部门筛选、按姓名搜索；**打字时跨部门搜全公司**，忽略当前选中的部门——
  用户打字就是因为不知道人在哪个部门，这时还按部门过滤等于帮倒忙
- 选完人自动切回「消息」页签：用户的意图是「跟这个人说话」，不是继续浏览通讯录
- 选 1 人 → 单聊。**同一对人只会有一个会话**：已存在就直接打开，不新建
- 选 2 人及以上 → 建群，默认群名为前 3 个成员的姓名拼接（`张明、李华、王芳`），可改
- 已离职（停用）的员工在选择器里不可选；历史会话仍可打开，但只读，顶部提示「对方已离职」

### 5.3 消息收发

- 输入框：`Enter` 发送，`Shift+Enter` 换行（在个人偏好里可对调，这是老后台用户的高频诉求）
- 支持直接**粘贴图片**、**拖拽文件**到窗口
- 发送后消息立刻上屏，状态为「发送中」；成功转为已发送，失败显示红色感叹号，点击重发
- **消息顺序以服务端为准**：本地乐观上屏的消息，收到服务端回执后按服务端序号归位
- 连续消息合并：同一个人 5 分钟内的连续消息合并显示，只在第一条显示头像与昵称
- 时间分隔：与上一条间隔超过 5 分钟时插一条居中的时间标签

**消息长度与频率**

| 限制 | 值 | 超出时 |
|---|---|---|
| 单条文本 | 5000 字 | 前端阻止，输入框下方提示 |
| 发送频率 | 20 条 / 分钟 / 人 | 429 + `Retry-After`，前端提示「发送过于频繁」 |

频率限制是防误操作和防脚本刷，不是反垃圾——内部系统没有陌生人。

### 5.4 未读与已读

- 未读数 = 会话最新序号 − 我读到的序号。**不存计数字段**，永远算出来，
  这样多设备之间天然一致（与 M2 系统公告「只记已读不记未读」是同一套思路）
- 打开会话且窗口处于前台时标记为已读；窗口在后台（切了标签页）**不算已读**
- 浏览器标题在有未读时显示 `(3) Keel 管理后台`，这是用户最常看的那块地方
- **单聊已读**：在自己发出的最后一条消息下方显示「已读」或「未读」，只标最后一条。
  逐条标已读在单聊里没有信息量——对方读到哪条，前面的必然都读过了

### 5.5 撤回与删除

**怎么触发**

| 端 | 入口 |
|---|---|
| 后台 | 鼠标悬停到消息上，时间戳旁出现「撤回」 |
| 移动端 | **长按消息**弹出操作菜单。文本一律带「复制」，撤回按条件出现——
没有可用动作时不弹一个只有「取消」的空菜单 |

⚠️ 移动端必须在气泡、图片、文件卡片上禁用 `-webkit-touch-callout`，
否则 WebView 会先弹自己的「复制 / 存储图片」把菜单盖掉，表现是「长按时好时坏」。
代价是文字不能手选，所以菜单里的「复制」不是可选项而是必需项。

| 操作 | 谁能做 | 时限 | 结果 |
|---|---|---|---|
| 撤回 | 消息发送人 | 2 分钟 | 双方都变成灰色提示「你撤回了一条消息」，原内容不再下发 |
| 撤回 | 群主 | 无限 | 显示「消息已被群主撤回」 |
| 删除（对我隐藏） | 任何人对自己可见的消息 | 无 | 只有自己看不到，对方不受影响 |

撤回后原内容**在库里保留但不再下发**——留给 §8 的审计，也避免误撤回后无法追溯。
产品上对用户表现为「撤回了」，这一点不暴露给前端。

### 5.6 群

- 建群无需审批，任何有 `chat:use` 的人都能建
- 群人数上限 **200**（V1 的技术上限，见技术文档 §6 的扇出估算）
- 加人：群主从员工选择器加，被加的人能看到**入群之前的历史消息**（内部群，透明优于隐私；
  若将来要改成「只能看入群后的」，成员表已经预留了起始序号字段）
- 踢人 / 退群：立即失去读写权限，历史消息从列表中移除
- 解散群：所有人的会话列表移除，消息保留在库里（审计需要）
- @：输入 `@` 触发成员选择，支持 `@所有人`（仅群主可用，防刷屏）

### 5.7 通知

| 通道 | 行为 |
|---|---|
| 站内 | 顶栏消息图标红点 + 数字，点击打开聊天页 |
| 浏览器桌面通知 | 窗口在后台且未免打扰时弹出，点击聚焦到对应会话。需用户授权，未授权不反复弹 |
| 提示音 | 默认开，个人偏好可关。同一秒内多条只响一次 |
| 移动端推送 | **不做**。需要接厂商推送通道，与「不绑死服务商」冲突；staff 在前台时走长连接，退到后台就收不到，这是 V1 已知且接受的限制 |

> M3 定案过「通知偏好不做」，理由是系统里没有通知消费方。聊天就是第一个消费方，
> 所以这一版把**聊天相关**的三个开关（桌面通知 / 提示音 / Enter 发送）加进个人中心，
> 但仍然不建通用通知中心——只为一个模块建平台是过早抽象。

### 5.8 历史与漫游

- 消息**只存服务端**，任何设备登录都能看到完整历史。本地不做持久化缓存
- 向上滚动到顶自动加载上一页，每页 30 条
- 留存期：默认 **365 天**，由系统参数 `chat.message.retainDays` 控制，
  清理走 M3 已有的定时任务 + 队列（与日志清理同一套机制，不新建轮子）

## 6. 界面

**入口两处**：顶栏的消息图标（带红点，点击进聊天页），左侧菜单「协同 / 消息」。

**布局**：独立整页 `/chat`，三栏收敛为两栏——

```
┌──────────────┬────────────────────────────────────┐
│ 会话列表      │  会话标题栏（名称 / 人数 / 设置）      │
│ 320px 固定    ├────────────────────────────────────┤
│              │                                    │
│ [搜索框]      │  消息区（虚拟滚动，向上翻页）          │
│ ▸ 置顶会话    │                                    │
│ ▸ 普通会话    │                                    │
│              ├────────────────────────────────────┤
│              │  工具条（图片/文件/emoji）             │
│              │  输入框（Enter 发送）                 │
└──────────────┴────────────────────────────────────┘
```

- **不做全屏弹窗式的悬浮聊天窗**。后台已经有多页签，再叠一层浮窗会和页签系统打架
- 消息区**不套 `ProTable`、不套 `PageSkeleton` 的 list 形态**——聊天是第六种页型，
  与现有五种（列表 / 表单 / 详情 / 树形 / 看板）都不同。要不要把它抽成模板，
  等这个模块跑稳之后再说（页型模板的原则本来就是「边做边抽」）
- 样式遵循 `web/docs/DESIGN.md`：气泡用中性灰 + 品牌色 `#409eff`，不引第三方聊天 UI 库
- 移动端 `staff/` 按 `staff/docs/DESIGN.md` 另做，会话列表用内嵌分组列表形态

## 7. 非功能要求

| 项 | 目标 | 怎么验 |
|---|---|---|
| 端到端时延 | P95 < 500ms（同机房） | 收发两端打时间戳，压测脚本统计 |
| 消息不丢 | 服务端返回成功的消息 100% 可被接收方拉到 | 断网 30s 后重连，比对两端序号连续 |
| 消息不重 | 同一条消息在任何设备上只出现一次 | 客户端幂等 ID，重发 100 次断言库里 1 条 |
| 消息不乱序 | 会话内严格按服务端序号展示 | 并发发送 500 条，断言序号无空洞无重号 |
| 并发连接 | 单机 2000 长连接稳定运行 30 分钟 | 沿用 M4 的压测方法，看内存斜率 |
| 内存 | WS 进程稳态 < 200MB @ 2000 连接 | 同上。**这是 webman 常驻内存的重灾区**，见技术文档 §7 |
| 重连 | 断线后 30s 内自动恢复，用户无感 | 拔网线、切 wifi、挂起笔记本三种场景各试 |

## 8. 数据留存与合规

- 消息内容在库里**明文存储**。不做端到端加密：企业内部 IM 的审计需求与 E2EE 直接冲突，
  二选一必须选审计。这一点应当在产品说明里对员工透明
- 留存 365 天后物理删除，附件同步删除
- **会话审计功能 V1 不做**，但数据结构已经支持（撤回保留原文、删除只是隐藏）。
  真要做时，流程必须是「申请 → 审批 → 限定范围与时间窗 → 全程记操作日志」，
  而不是给管理员一个「查看任意聊天记录」的按钮。这是单独立项的东西

## 9. 验收清单

每条都要**真点一遍**，类型检查和单测发现不了这些。

> **勾选的含义**：`[x]` = 已验证并注明验证方式；`[ ]` = 未验或功能未做。
> 验证方式分三档，**不要混为一谈**：
> `脚本` = curl / WS 客户端跑的断言 · `浏览器` = 后台界面真点过 · `真机` = 移动端设备上验过。
> **截至 2026-09-20，移动端一条「真机」都没有**——只验到接口层与 SFC 能编译（staff/CLAUDE.md 的既有要求）。

**基础收发**（每一条都要**跨设备**验一遍：手机发、电脑收，以及反过来）
- [x] A 发文本，B 的窗口在 1 秒内出现，不需要刷新 —— `脚本`+`浏览器`
- [x] 手机上发出的消息，电脑端实时出现；电脑发的，手机实时出现 —— `脚本`
      （打的是 `/staff/v1/*` + 长连接，**不是真机界面**）
- [x] A 发图片 / 文件，B 能预览 / 下载 —— `脚本`+`浏览器`
      （跨端也验过：移动端接口传图 → 后台长连接收到，宽高一并带过来）
- [x] B 的窗口在后台时收到桌面通知，点击能聚焦到对应会话 —— `浏览器`（开关与面板）
      ⚠️ **通知本身没有端到端验过**：需要真的把窗口切到后台再让别人发消息，
      而权限弹窗与系统通知都在浏览器沙箱之外。代码路径是
      `document.hidden` + `Notification`，逻辑核对过但没见过实际弹窗
- [x] 发送失败显示重发按钮，点重发能成功 —— `浏览器`
      （复用原 `client_msg_id`，服务端幂等，不会变成两条。
      **「断网时发」这个具体场景没模拟**，验的是失败态与重发路径）

**一致性**
- [x] A 在电脑和手机同时登录，两端消息完全一致，未读数同步 —— `脚本`
- [x] 刷新页面，会话列表、未读数都还在；**在会话之间切换时滚动位置保留** —— `浏览器`
      （刷新后仍然回到底部，那是「我来看新消息」的语义，不是缺陷；
      记忆只存在内存里，不跨刷新）
- [x] 拔网线 30 秒再插上，中间对方发的消息全部补齐，**且顺序正确、没有重复** —— `脚本`
      （用 `after_seq` 模拟断线补齐，**真拔网线没试过**，第 ⑥ 批）
- [x] 连点 10 次发送同一条消息（模拟卡顿），库里只有该发的条数 —— `脚本`
      （并发 100 条 0 失败、seq 连续无重号）

**未读与已读**
- [x] 顶栏红点数 = 会话列表未读之和 = 浏览器标题里的数字 —— `脚本`
      （验的是**服务端口径**：列表未读之和 18 = 全局汇总 18。前端三处都派生自同一个
      store，但没在界面上逐一比对过）
- [x] 免打扰的会话有未读时不计入全局数字，只显示小圆点 —— `脚本`
- [x] 打开会话后红点清零 —— `脚本`+`浏览器`；窗口切到后台时收到的消息**不算已读**
      —— 代码里有 `document.hidden` 判断，**没真切标签页验过**
- [x] 单聊里对方读了之后，我最后一条消息下方出现「已读」—— `脚本`+`浏览器`
      （服务端广播验过；界面上「未读」能正常显示。
      ⚠️ 刷新后的初始水位用的是**保守近似**——只要我不是最后一个发言的人就算对方读过，

## 10. 里程碑拆分

**后台与移动端同步交付，不分先后。** 每一批做完都要「手机发、电脑收」真点一遍——
这是这个模块最有效的验证方式，也是批次边界的划分依据。执行细节见
[技术方案 §10](chat-tech.md#10-实施拆分双端并行)。

| 批 | 内容 | 做完能干什么 |
|---|---|---|
| **① 地基** ✅ | 通用文件上传 + 双端联调环境打通 | 手机能登进本地后端，图片传得上去（`233f4ba` `adf6a25`） |
| **② 一条消息跑通** ✅ | 表 + 长连接 + 收发接口 + 两端最简聊天页 | **手机发一句，电脑 1 秒内看到** |
| **③ 会话列表与未读** ✅ | 会话列表、建会话、未读红点、已读 | 像个能用的聊天工具了 |
| **③.5 通讯录** ✅ | 组织架构只读视图，后台是消息页里的页签，移动端是独立 tab | 不打开聊天也能查同事 |
| **④ 富消息与撤回** ✅ | 图片、文件、撤回、已读标记、失败重发 | 能发照片和文件，发错了能撤 |
| **⑤ 群聊** ✅ | 建群、成员管理、群主撤回、@（服务端） | 群里能协作 |
| **⑥ 打磨与压测** | 虚拟滚动、断线重连、桌面通知、暗色模式、2000 连接 30 分钟 | 可以交付 |

第 ② 批最重，也最难拆——聊天这东西「后端通了但没有界面」等于什么都验证不了，
所以它必须一口气做到两端能互发。风险集中在这一批，后面几批反而可以按需停。

⚠️ 和 M4 一样，**压测不能与其他测量并行**——测连接数时跑功能用例，
内存曲线就说不清是谁涨的。
