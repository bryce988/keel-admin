## 0. 前置：先做这三件，再碰模块

七个模块的页面结构高度重合。不先把重合部分收敛掉，就会写出七套各不相同的实现。

- [x] **P1 `ProTable` 列表状态同步到 URL**（M1 遗留）
  - 分页、排序、筛选条件写进 query string，刷新后还原
  - 用 `router.replace` 而不是 `push`：翻十页就往历史里塞十条，返回键会变得没法用
  - 数字型筛选字段必须在 `paramParsers` 里登记（`{ status: Number }`）——
    URL 里的值**永远是字符串**，不转的话 `el-select` 显示空白、树的选中态对不上
  - 多页签必须存 `fullPath` 而不是 `path`，否则切走再切回来筛选条件全丢，前面白做

  **验收**（每条都要真点一遍，类型检查发现不了这些）
  - [x] 改筛选 / 翻页 / 排序，地址栏跟着变；默认值（第 1 页、默认 pageSize）不写进 URL
  - [x] 刷新页面，筛选条件、页码、排序原样回来
  - [x] 切到别的页签再切回来，条件还在
  - [x] 点「重置」不报错，且地址栏参数被清空
  - [x] 树形筛选（部门树）刷新后**选中高亮还在**——这条最容易翻车，验的是 `paramParsers`
  - [x] **改完筛选立刻取数，用的是新值**——见下方「已踩过的坑」

  **已踩过的坑**：`params` 是 prop，页面整体赋值（`query.value = {...}`）后
  要等父组件重新渲染才传得进来。若 `reload()` 不等这一拍，`fetch()` 读到的是**上一次**的
  筛选值——表现为点部门树数据慢一拍，来回点两个部门就完全对调。
  修在 `ProTable.reload()` 里 `await nextTick()`，**不要**让每个页面自己 await：
  七个模块二十几个筛选交互，总有一处会忘，而且这种 bug 不报错，只是数据悄悄错一拍。
- [x] **P2 表单抽屉规范**
  - `FormDrawer` 只统一「壳」——打开、深拷贝、校验、提交、loading、错误回填、关闭；
    字段用插槽自由写。schema 驱动放弃了：菜单表单光 type 就有五种形态，
    会长出一堆 `show: (form) => ...` 谓词，变成没人愿意读的小框架
  - 深拷贝再编辑：直接编辑列表行对象的话，没点保存表格就变了，取消也回不去
  - 服务端错误两条回填路径：422 按 `details` 逐字段对号入座；
    409/400 只有一条 message，靠 `errorFields`（业务码 → 字段名）落到输入框
  - 失败时弹窗不关，用户可以直接改
  - 用抽屉而不是弹窗：后台表单字段普遍偏多，弹窗撑不下就要在内部再套一层滚动；
    抽屉天然是整列高度，长表单不用二次滚动，也不会把列表整个盖住
  - `mode: 'view'` 覆盖详情场景：隐藏确定按钮，页面在插槽里改用 `el-descriptions`
    渲染，而不是给一堆禁用的输入框——只读场景下输入框既占地方又误导
  - 实例类型 `FormDrawerInstance` / `ProTableInstance` 统一从 `@/components` 导出，
    页面不各写各的内联注解，否则组件加参数时只有用到的那页会报错，别处悄悄过
  - 用顶栏「修改密码」做了真接口验证，顺带填掉了那个“将在 M2 实现”的占位
- [x] **P3 后端写接口的通用件**
  - `Guard`：`found` / `unique` / `notReferenced` / `noCycle` / `notBuiltin`
  - `BatchResult`：批量操作逐条尽力执行，返回成功与失败明细
  - **`unique` 必须 `withoutGlobalScopes()`**，两个理由缺一不可：
    绕过数据权限（否则受限用户看不到别人部门的编码，会「成功」创建重复值再撞
    唯一索引，用户看到的是 500 而不是「编码已存在」）；算上软删的行
    （`uk_code` 不含 `deleted_at`，软删记录仍占着编码）
  - **`notReferenced` 恰恰相反，保留软删 Scope**：已软删的用户不该拦住删除其部门。
    「谁看得见」和「这条能不能删」是两回事
  - `noCycle` 用**向上回溯 parent_id** 而不是查子孙集合：部门有 ancestors、
    菜单只有 parent_id、角色继承又是另一套，向上走三处都能复用；带 64 层深度上限
  - `BatchResult` **只吞 `ApiException`**：数据库连不上、代码写错必须继续上抛，
    把真正的 bug 伪装成「这条数据删不掉」是排查时最耗时间的误导

  **验收**：脚本对着真实数据跑了 15 项，全过——含「软删记录仍占用编码」
  「数据权限受限的用户也能查出重复」「非业务异常不被吞掉」三条最容易漏的。

**预计 1.5 天。** 后面七个模块每个能省掉大半天。

## 1. 阶段与顺序

顺序按 **RBAC 三层（定义 → 授权 → 分配）+ 依赖关系** 排，不是随便挑的。

### M2.1 部门 + 岗位

**为什么第一**：它是数据权限的载体，后面每个模块的归属过滤都依赖它；且零依赖。

- [x] 后端 `depts` CRUD：新建、编辑、删除、树查询
  - 移动部门时**同步刷新所有子孙的 `ancestors`**（database.md §3.2），
    用一条 `UPDATE ... CONCAT(?, SUBSTRING(ancestors, ?))` 完成，不递归 save——
    子树可能几百个节点，逐个存既慢又可能中途失败留下半更新状态，那时权限就是错的
  - 上级不能是自己或自己的子孙（400 + `20202`）
  - 有用户、岗位或子部门时不可删（409 + `20203`）
- [x] 后端 `posts` CRUD（含批量删除）
- [x] 前端 部门树表页 —— `ProTable` 加了 `tree` 模式：不分页、request 返回数组。
      树必须一次给全，只给一页的树是断的，父节点被翻到下一页就成了孤儿
- [x] 前端 岗位列表页（多选批量删除，失败明细逐条列出而不是笼统一句「操作失败」）

**验收**（已通过）：一级组挂在技术部下时 manager 可见 `manager/dev01/probe`，
把一级组移到运营部后**同一个 token、不重新登录**再查，只剩 `manager/dev01`——
说明 `ancestors` 真的刷新了，且全局 Scope 读到了新值。

**踩到的坑**：树形筛选**不能写进 SQL**。`where status=1` 会把停用的父部门滤掉，
它下面启用的子部门也跟着从树上消失。正确语义是「命中的节点连同祖先链一起保留」，
已抽成 `filterKeepingAncestors(nodes, callable)`，部门树与菜单树共用。

### M2.2 菜单与权限（**定义**层）

**为什么第二**：RBAC 的定义层，角色授权要勾它；做完立刻能验证动态路由。

- [x] 后端 `menus` 树查询 / CRUD
  - 权限点被角色引用时不可删，只能停用（409 + `20402`）
  - 上级不能是自己或子节点（400 + `20403`）
- [x] 前端 菜单树表 + 节点表单
  - 五种 `type` 的表单字段**完全不同**：目录没有 `api_path`，按钮没有 `component`，
    数据(字段)权限只有名称与标识。表单要按 type 动态切换，不要堆成一个大表单
- [x] 前端 角色×权限审计矩阵（只读）

**验收**：新增一个菜单 → 授权给某角色 → 该角色的用户刷新页面就看到，**全程不发版**。
这条是「不写死菜单」这个设计成立与否的唯一证据。

**验收情况**：界面部分已通过（超管跳过权限校验直接拿全量菜单，新建的菜单刷新就在侧边栏）。
⚠️ **「授权给某角色 → 该角色用户看到」这半条只在后端用 SQL 验过**，
授权前 manager 的菜单是 5 项、SQL 授权后变 6 项。角色管理页当时还没有，界面上点不出来。
**留到 M2.7 用真界面补验**——SQL 绕过了服务端递增 `perm_version` 的逻辑，验的只是半条链路。

### M2.3 角色（**授权**层）

依赖 M2.1（数据范围要选部门）、M2.2（权限树）。

- [x] 后端 `roles` CRUD（内置角色不可改删，403 + `20302`）
- [x] 后端 `grantPerm` 保存功能权限 → 递增持有者的 `perm_version`
  - **服务端自动补齐祖先链**：前端树只回传勾中的叶子，父目录不带上的话
    `buildMenuTree` 从根找不到这条链，**整个菜单会消失**。与其要求每个调用方
    记得补，不如服务端兜住。实测只授 `sys:dict:create` 会落库三条（目录→菜单→按钮）
- [x] 后端 `grantData` 保存数据范围（含 `data_scope=5` 时的 `sys_role_depts`）
- [x] 后端 字段级权限 —— **待定问题 ② 已定：不做单独界面**。
      字段权限就是 `type=5` 的权限点（`sys:field:user:phone`），跟权限树一起勾。
      `sys_role_fields` 表保留不用，两套机制并存只会让人搞不清哪个说了算
- [x] 后端 角色成员的增删（与用户管理的「分配角色」共用 `assertAssignable`，
      两处实现必然漂移，漂移的表现是「从角色页能加、从用户页加同一个人却被拒」）
- [x] 前端 角色列表 + 授权抽屉（功能权限 / 数据范围 / 职责分离 三个 tab）+ 成员抽屉
  - 权限树的父子联动、继承来的节点置灰不可取消
  - 互斥角色（400 + `20304`）、角色数上限（`20305`）、继承环（`20306`）三个校验
  - 新增 `sys_role_mutexes` 表，互斥**对称存两条**——否则查询要写
    `where role_id=? or mutex_id=?`，那种两边都要考虑的条件总有一处会漏

**验收**（已通过）：manager 调 `/admin/roles` 先是 403 → admin 给它的角色补上
`sys:role:list` → **用同一个旧 token** 再调变 200，全程没重新登录。

**顺带清掉一条 M1 遗留**：五种数据范围逐个实测过了——
全部 4 人 / 本部门及下属 2 人 / 本部门 2 人 / 仅本人 1 人 / 自定义(仅运营部) 1 人。

## 2. 待定：开工前需要拍板的三件事

### ① 导入导出用什么

| 方案 | 优点 | 代价 |
|---|---|---|
| **纯 CSV**（倾向） | 零依赖，内存友好 | 不支持样式与多 sheet |
| PhpSpreadsheet | 功能全，支持模板 | 20MB+ 依赖，且**吃内存**——常驻进程下要格外小心 |

**倾向 CSV**：脚手架不该为了导出背一个重依赖，真需要 Excel 的项目自己加。
无论选哪个，导出都必须走 chunk 分批，不能一次 `get()` 全表（CLAUDE.md 常驻内存红线）。

### ② 字段级权限的界面 —— ✅ 已定（M2.3）

**结论：不做单独界面。** 字段权限就是 `sys_permissions` 里 `type=5` 的权限点
（`sys:field:user:phone`），跟功能权限一起在授权抽屉里勾，服务端在接口返回前脱敏。

`sys_role_fields` 表保留结构但**不使用**——两套机制并存只会让人搞不清哪个说了算。
将来真需要「按对象×字段精细配置」时再启用，那时也只该有一套生效。

### ③ 五种页型模板（M3）现在抽还是最后抽

**倾向边做边抽**：M2.1 写第一个树表页时就抽成模板，M2.2 的菜单树直接复用。
等七个模块都写完再回头抽，等于把七份代码重写一遍。
这样 M3 会自然缩水成「补文档 + 补缺的两种页型」。

## 3. 贯穿始终的约束

每个模块开工前重读一遍 CLAUDE.md 的硬性约定，尤其这几条：

- 新增写接口必须在 `config/route.php` 声明 `perm`，**不写就是 403**；写接口还要带 `log`
- 数据权限由模型全局 Scope 注入，**禁止业务代码手写归属过滤**
- 控制器不查库不拼状态码；事务只在 service 层
- 前端不写死颜色、枚举、菜单；列表页统一用 `SearchForm` + `ProTable`
- 接口字段一律 snake_case，与数据库字段名逐字一致
- 表结构改动写进 `server/database/schema.sql`，权限点/字典改动写进 `scripts/seed.php`
